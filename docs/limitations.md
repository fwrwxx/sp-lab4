# Реєстр обмежень super loop (ЛР3)

## Обмеження 1: довга операція (flash/SPI) блокує реакцію на подію

**Симптом.** У S3 команда UART, яка в S1 виконується за 9 мкс, під час `long_op` виконується за **81 360 мкс (81 мс)**. IMU джитер зростає з **4 581 мкс** (S1) до **84 826 мкс** (S3). Кнопка, натиснута під час `long_op`, обробляється із затримкою ≈ 80 мс.

**Доказ.** `docs/metrics/S1.log` (`uart_cmd max_us=9`), `docs/metrics/S3.log` (`uart_cmd max_us=81360`, `imu jitter_max_us=84826`, `long_op max_us=80424`). Logic Analyzer `docs/captures/lab3.vcd`: канал `PROBE_LONG` (PA9) високий ~80 мс, на цьому інтервалі `PROBE_IMU` (PA8) не пульсує.

**Причина в архітектурі.** Super loop виконує задачі послідовно; `long_op_task` — блокуючий busy-wait + SPI. Немає витіснення, тож `button_task`/`uart_cmd_task` чекають завершення.

**Як обійти без ОС.** Розбити `long_op` на кроки (машина станів) + DMA для SPI; `button_task` перенести в EXTI ISR; `uart_cmd` — у USART ISR (уже частково так). Ціна: складність коду, ризик reentrancy, потреба в чергах, важче налагоджувати.

**Що дала б ОС.** Пріоритетне витіснення: `button` (високий) перериває `long_op` (низький). Семафор/черга між ISR і задачею. Timeout у блокуваннях.

**Ціна ОС.** ~2–4 КБ RAM на стеки (у вас RAM вільна ~9.5 КБ), накладні витрати перемикання (~5–10 мкс), нові класи помилок (інверсія пріоритетів, deadlock, stack overflow у задачі).

**Гіпотеза ЛР4.** `imu jitter_max_us` у S3 впаде з **84 826 мкс** до **< 1 000 мкс** при пріоритетах `IMU > flash`. `uart_cmd max_us` впаде з **81 360** до **< 100 мкс**.

## Обмеження 2: bit-bang I2C обмежує частоту IMU

**Симптом.** `imu.avg_us = 8 347 мкс` (8.3 мс). Замість 200 Гц (5 мс) IMU фактично опитується ~120 Гц. `missed = 2` навіть у S1 (без навантаження).

**Доказ.** `STAT name=imu n=1181 avg_us=8347` у S1. Logic Analyzer: транзакція I2C на PB8/PB9 триває ~8 мс через `i2c_delay()`.

**Причина в архітектурі.** Це не super loop, а драйвер: `board.c` використовує bit-bang I2C (через аномалію HAL I2C з ЛР2). Але наслідок для super loop: періодична задача не встигає, `missed > 0` навіть без довгих операцій.

**Як обійти без ОС.** Апаратний I2C1 у режимі IT/DMA; або зменшити `i2c_delay` до 1–2 ітерацій. Ціна: може не працювати в Wokwi (аномалія HAL I2C), ризик NACK.

**Що дала б ОС.** Нічого — ОС не прискорює шину. Але ОС дозволила б винести I2C-транзакцію в окрему задачу з низьким пріоритетом, а інші задачі виконувались би паралельно під час очікування шини.

**Гіпотеза ЛР4.** З FreeRTOS + апаратним I2C `imu.avg_us` впаде з **8 347** до **~250 мкс**, `missed` = 0 у S1.

## Обмеження 3: важко додати нову задачу зі своїм періодом

**Симптом.** Щоб додати `lcd_task` (раз на 500 мс), довелось вставити виклик у `App_Loop()` і перевірку часу в самій задачі. При додаванні 5-ї задачі — 5 місць правок у `App_Loop` + 5 нових `perf_stat_t`.

**Доказ.** `App/Src/app.c` — `App_Loop()` містить виклики 5 задач послідовно, кожна має свій `if (perf_now() - prev < period) return;`.

**Причина.** Немає планувальника: кожна задача — окремий виклик + власна перевірка часу + власна глобальна змінна `_t_prev`.

**Як обійти без ОС.** Таблиця задач (як time-triggered scheduler у Pont): масив `{fn, period, next_run}`, один цикл у `App_Loop`. Ціна: ще один рівень абстракції, складніше налагоджувати.

**Що дала б ОС.** `xTaskCreate(task_fn, ..., period, ...)` + `vTaskDelayUntil(...)` — задача сама знає свій період, планувальник запускає.

**Гіпотеза ЛР4.** Додавання `lcd_task` — 3 рядки коду замість 5 місць правок.

## Обмеження 4: блокування на таймаутах HAL

**Симптом.** `flash_log.max_us = 8 283` мкс (S3) — це `W25Q64_ReadJedec` + `bus->delay_ms(1)`. Якщо flash відмовить, `HAL_SPI_TransmitReceive(..., 100)` блокує на 100 мс — вся система стоїть.

**Доказ.** `docs/metrics/S2.log` — `flash_log.max_us=20025` (20 мс) при періодичному записі. Logic Analyzer — на інтервалі `CS#=LOW` (PB6) `PROBE_IMU` не пульсує.

**Причина.** `HAL_SPI_TransmitReceive` — блокуючий. Немає таймаутів на рівні задачі.

**Як обійти без ОС.** SPI у режимі IT/DMA + машина станів; таймаут на рівні задачі (перевіряти `HAL_GetTick()` у циклі).

**Що дала б ОС.** `xSemaphoreTake(spi_bus, timeout)` — задача блокується, але інші виконуються. Timeout = автоматичний.

**Гіпотеза ЛР4.** `flash_log.max_us` = 20 мс → під FreeRTOS IMU не блокується, `imu_jitter_max` < 1 мс.

## Обмеження 5: спільні дані між ISR і super loop

**Симптом.** `cmd_buf` у `cmd.c` пишеться з `USART2_IRQHandler`, читається з `cmd_poll()` у super loop. Використовується `volatile uint8_t cmd_line_ready` — але без критичної секції навколо `memcpy(cmd_line, cmd_buf, ...)`.

**Доказ.** `App/Src/cmd.c` — `cmd_rx_byte()` (ISR) і `cmd_poll()` (loop) працюють з `cmd_buf`/`cmd_line`. Якщо новий байт прийде під час `memcpy` — можливе побиття.

**Причина.** Немає механізму міжпоточної синхронізації, окрім `volatile`. `volatile` не гарантує атомарності `memcpy`.

**Як обійти без ОС.** Кільцевий буфер + атомарні `head`/`tail` + критична секція (disable IRQ) навколо `memcpy`. Ціна: новий код, ризик забути критичну секцію.

**Що дала б ОС.** `xQueueSendFromISR` / `xQueueReceive` — атомарно, без критичних секцій вручну.

**Гіпотеза ЛР4.** 0 збоїв парсингу команд при 10× навантаженні.

## Що super loop робить краще за ОС (перевірити в ЛР4)

- **Детермінізм у S1.** `loop.max_us` = 16 406 мкс стабільно, розкид ±1%. ОС додасть варіабельність від перемикань контексту.
- **Пам'ять.** RAM 2 736 B (22%). FreeRTOS додасть ≥ 2–4 КБ на стеки задач.
- **Час старту.** `APP init` до першого `loop` — мілісекунди. FreeRTOS — додатково ініціалізація ядра.
- **Простота налагодження.** Один стек, один `while(1)`, без стеків задач, без пріоритетів.
